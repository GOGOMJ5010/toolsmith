An agent can only press the buttons it is given. A WebMCP site hands an agent a fixed set of them, decided by whoever built the site. When the one you need is not there, the agent guesses, scrapes, or hands you a snippet to run yourself. Adding a real one today means writing an MCP server, hosting it, editing a config file and restarting the client — for a function you might use once. Toolsmith moves that from days to seconds without moving it out of your sight.

A button you did not read is not a button you granted. So nothing is registered until you approve it; the code stays open on screen and editable, with a Test run that executes against your real data before the button exists. Every call runs in a fresh Web Worker with fetch, XMLHttpRequest, WebSocket and storage deleted from the global scope first, on a three-second leash. Editing a granted button takes it back for re-approval. Reloading returns every button to pending. Every call is logged.

How it works. The interface says button because that is what it is to a person; the WebMCP spec calls it a tool. Toolsmith registers five permanent tools on document.modelContext. One of them, forge_tool, takes a name, a JSON Schema and a JavaScript body and turns them into a real tool the same agent can call seconds later — registered with its own AbortSignal, so taking it back is one abort().
